## The new exam format (the biggest reveal)

!!! success "Straight from the professor — memorize this"
    - **Two question types:** standard MCQs matching previous papers, plus **new
      subjective scenario-based questions** testing critical thinking rather than rote
      definitions.
    - **Subjective questions are graded by LLMs** (AI-graded, not humans). Success
      depends on organizing, structuring, and justifying your answers clearly enough
      to *"convince the LM."*
    - **Example subjective scenario:** you're talking to a client — *"What are the
      three most important follow-up questions you would ask based on these
      requirements?"* — testing capabilities, constraints, and business context.
    - **For the LLM grader:** use bullet points and clear headers. It grades on
      logical markers and "thinking" keywords: **constraints, assumptions,
      scalability.**
    - **On answer length:** "logic over length" — a reasoned solution that demonstrates
      critical thinking, not a high word count.

→ Our full method: [Writing answers an LLM grades well](../exam/llm-grading-guide.md)

!!! danger "Syllabus exclusion"
    **OpenRefine is NOT on this term's syllabus.** If you encounter OpenRefine
    questions in older papers (text clustering, name standardization), skip them
    immediately.

## Concepts the professor stressed

### Parquet — the "odd one out"

JSON, XML, CSV: all text-based, all "flat," all carrying overhead for large numeric arrays. **Parquet is columnar** — the efficient choice. When a question groups these formats and asks about efficiency, the columnar outlier is the answer.

→ [Solved: T3-2025 FN Q2](../pyqs/t3-2025-fn.md#q2-parquet-for-large-arrays)

### Git lifecycle — the "safety goggles"

`git status` and `git diff` are the goggles you wear **before** the welding of commit and push. He walked the full family: `status` (what changed), `diff` (what lines), `log` (history), `show` (one commit in detail).

→ [Solved: T3-2025 FN Q3](../pyqs/t3-2025-fn.md#q3-git-diff)

### HTTP status codes — the full taxonomy

He taught the complete family with the 401/403 distinction: **401 = not logged in** (like viewing private Instagram content without an account); **403 = logged in but lacking permission**. 429 = rate limit, often handled by the API library itself. 500 = generic server-side failure where the client request was valid.

→ [Solved: T3-2025 FN Q4](../pyqs/t3-2025-fn.md#q4-http-429)

### API validation — fail fast with schemas

External APIs are unpredictable. **Fail-fast schema validation** — auditing types and value ranges the moment data arrives — is superior to letting errors propagate downstream. Explicit fallbacks prevent one API failure from crashing the pipeline.

→ [Solved: T3-2025 FN Q7](../pyqs/t3-2025-fn.md#q7-validating-external-api-data)

### ETL — lookback windows, not full reprocessing

Late-arriving data is the challenge. Reprocessing all history daily is *"cost-extensive"* — wasted compute, excessive time, database lockups. The professional pattern: **lookback windows** (last few days) + **deduplication** via unique IDs and update timestamps.

→ [Solved: T3-2025 FN Q8](../pyqs/t3-2025-fn.md#q8-late-arriving-orders)

### Dashboard caching — TTL arithmetic

A dataset updating hourly, queried every few seconds: the middle layer saves the database. A **5-minute TTL** means the database is hit once per 5 minutes regardless of how many users view. Freshness vs conservation, balanced by the number.

→ [Solved: T3-2025 FN Q9](../pyqs/t3-2025-fn.md#q9-caching-an-hourly-updated-dashboard)

### Timezones — the assumption that corrupts

Assuming missing timestamps are UTC is *"a common and dangerous pitfall that leads to silent data corruption."* The professional approach: infer from metadata or geography, **document** the assumptions, **flag** inferred values for auditing.

→ [Solved: T3-2025 FN Q10](../pyqs/t3-2025-fn.md#q10-joining-across-timezones)

### Docker — the EXPOSE misconception

**EXPOSE is documentation** — a label telling other containers which port the app listens on. It is **not** a bridge to the host. Only the `-p` flag at runtime maps the port to the outside world. A student asked if they'd see a Dockerfile in the exam: the file itself may not always be displayed, but you're expected to understand the logic of the build process.

→ [Solved: T3-2025 FN Q31](../pyqs/t3-2025-fn.md#q31-what-expose-does)

### The restaurant reviews case study (pandas)

The full scenario: review data in CSV with ratings, text, timestamps. The workflow he taught:

- Missing `review_text`? **Drop those rows** for text analysis: `df.dropna(subset=['review_text'])` — keeping nulls "provides zero value for text analysis and skews your statistics"
- Common words in negative reviews? **Filter first** (`rating < 3.0`), then extract and count
- Average rating by cuisine? **`df.groupby('cuisine')['rating'].mean()`** — the exact line, case-sensitive column names
- Sharing with a non-technical manager? **CSV** — portability and ease of use

→ [Solved: T3-2025 FN Q18–22](../pyqs/t3-2025-fn.md#q18-missing-review-text)

### Rapid-fire best practices

His list, verbatim:

- **Versioned pipelines:** always version transformation logic — it changes more frequently than the data schema
- **Currency storage:** store the original amount plus the specific exchange rate used, for future audits
- **Recommendation auditing:** use systematic segment analysis to fix poorly performing recommendations
- **Third-party assessment:** evaluate security vulnerabilities in external libraries before updating
- **Docker reproducibility:** use containers and pinned dependencies — "it works on my machine" must translate to the server
- **PII minimization:** retain only fields necessary for the specific utility

## Exam-engineering tips (his own framing)

!!! success "Two patterns he named explicitly"
    - **The 'Odd One Out' technique:** in serialization questions, if you see XML, JSON
      and CSV grouped together, recognize they're all text-based. Parquet, the columnar
      outlier, is almost certainly the correct answer for efficiency queries.
    - **The 'Longest Option' pattern:** in engineering exams, the most detailed answer
      — the one defining constraints, documenting assumptions, addressing edge cases —
      is frequently correct because it mirrors professional best practices.

!!! warning "His MCQ prep advice"
    The MCQ section is designed to be accessible. **Reviewing previous year questions
    is the single most effective use of your study time.** The options themselves are
    designed to guide you — systematic elimination works.
