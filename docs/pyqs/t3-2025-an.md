### Q3 · Listing hidden files · 🟢 Easy
**Topic:** Bash · **Asked in:** T3-2025 AN

> Which command lists hidden files in a Unix-like shell?
>
> A. `ls -h`  B. `ls -a`  C. `show -a`  D. `dir /ah`

??? success "Answer"
    **B** — `ls -a` shows all entries, including dotfiles.

??? note "Why"
    Files starting with `.` are hidden by default; `-a` (all) reveals them. The trap
    is `-h`: it looks like "hidden" but means **human-readable file sizes** (`ls -lh`
    gives "4.0K" not "4096"). Flag letters are reused across commands — trust usage,
    not mnemonic vibes. (`dir /ah` is Windows CMD — real flag, wrong shell.)

### Q4 · HTTP 401 · 🟢 Easy · ⭐⭐
**Topic:** HTTP status codes · **Asked in:** T3-2025 AN + FN, ET-2

> In the context of APIs, an HTTP 401 response means:
>
> A. Resource not found  B. Authentication required or failed  C. Server error  D. Rate limit exceeded

??? success "Answer"
    **B** — you are not (validly) logged in.

??? note "Why"
    The code family the ET-2 session drilled:

    - **401 Unauthorized** — who are you? Missing/invalid credentials.
    - **403 Forbidden** — I know you; you may not do this. (The professor's example:
      logged in, but viewing someone else's private content.)
    - **404** — no such resource · **429** — too many requests · **5xx** — the server's fault.

    🟡 The classic confusion is 401 vs 403: *identity* vs *permission*. One is a locked
    door with no key; the other is a key that doesn't fit this lock.

### Q7 · Catching silent schema drift · 🟡 Medium
**Topic:** Testing · **Asked in:** T3-2025 AN

> When designing small-unit tests for data cleaning functions, which assertion is most valuable to catch silent schema drift?
>
> A. Assert the function runs without exception.
> B. Assert that output contains expected column names and types.
> C. Assert execution time is below threshold.
> D. Assert the number of input files.

??? success "Answer"
    **B** — check the schema itself: columns present, types right.

??? note "Why"
    "Silent schema drift" is the failure where a column renames itself or a date
    becomes a string — the code still *runs*, so A passes while everything downstream
    quietly corrupts. The test that catches it must assert **structure**: column
    names and dtypes. Time (C) and file counts (D) measure everything except the
    contract.

    Same philosophy as GA0's property-based testing ([T1-2026 AN
    Q10](t1-2026-an.md#q10-property-based-testing-invariant-medium-star)): test
    *invariants*, not anecdotes.

### Q8 · Normalizing messy names · 🟡 Medium
**Topic:** Data cleaning · **Asked in:** T3-2025 AN

> You extract customer names from multiple sources: some return "John Smith", others "smith, john". After combining, you notice duplicates differing only in name format. Which approach best handles this?
>
> A. Keep both formats since they contain the same information.
> B. Normalize to first/last name components, standardize case/order, then deduplicate.
> C. Delete all records appearing as duplicates arbitrarily.
> D. Require users to manually resolve each formatting issue.

??? success "Answer"
    **B** — standardize first, then dedupe on the clean key.

??? note "Why"
    Deduplication needs a **canonical key**: parse names into components, normalize
    case and order, then "John Smith" and "smith, john" collapse to the same thing and
    dedup becomes trivial. Deduping *before* normalizing (C, A) either keeps duplicates
    or deletes the wrong rows; D doesn't scale past ten records.

    The pattern generalizes everywhere: **normalize → key → dedupe** (product names,
    company names, addresses — same recipe, and it's why fuzzy-matching is hard, see Q10).

### Q9 · Testing against a flaky external API · 🟡 Medium · ⭐
**Topic:** Testing · **Asked in:** T3-2025 AN, ET-2 (fallbacks)

> Your team uses an external weather API in automated tests. The API sometimes returns temporary errors (500s). Which testing approach is most reliable?
>
> A. Test against the live API every time, accepting occasional 500 failures.
> B. Record real API responses as offline test files, use files normally, test live periodically.
> C. Skip API tests since the provider handles reliability.
> D. Mock the API by hardcoding expected weather values for specific cities.

??? success "Answer"
    **B** — recorded fixtures for daily tests, live checks occasionally.

??? note "Why"
    The professional ladder this question walks: never let third-party flakiness break
    *your* CI (A), but don't fake the data shape either (D — hardcoded mocks drift from
    reality and test nothing). **Record real responses once, replay them offline** —
    your tests are deterministic *and* shaped like the truth — then a small periodic
    live test catches contract changes.

    ET-2's adjacent principle: external APIs are unpredictable; design fallbacks and
    fail fast. Same worldview, applied to testing.

### Q10 · Why text matching fails on products · 🔴 Hard
**Topic:** Data cleaning · **Asked in:** T3-2025 AN

> Supplier A lists "Blue T-Shirt Size M"; Supplier B lists "tshirt blue m". Why is simple text matching insufficient to identify these as the same product?
>
> A. The names include extra descriptive words not in both listings.
> B. Effective comparison requires accounting for word order, abbreviations, and synonyms — a simple word-by-word match is insufficient.
> C. Text matching is impossible with product names.
> D. The product codes are different so they must be different products.

??? success "Answer"
    **B** — normalization must handle order, abbreviations and synonyms before matching.

??? note "Why"
    The same normalize→key→dedupe recipe as [Q8](#q8-normalizing-messy-names-medium),
    but with the difficulty turned up: real entity matching needs lowercasing, stopword
    removal, synonym/abbreviation handling ("size M" ↔ "m"), maybe embeddings for
    semantics. A is *true* but shallow — it names one symptom, not the requirement; the
    exam wants the general rule. C and D are defeatism and key-worship.

### Q11 · Idempotent ETL scripts · 🟡 Medium · ⭐
**Topic:** ETL · **Asked in:** T3-2025 AN, T3-2025 FN (lookback), GA2

> In a bash ETL script that runs on a schedule, what should you do to make sure the job can run repeatedly without causing bad or duplicated results (i.e., to keep it idempotent)?
>
> A. Always write straight into the final output file and overwrite it every time.
> B. Write to a temp file, atomically move to final, track processed records.
> C. Delete all output files at the start of every run.
> D. Run the job several times at once so at least one run succeeds.

??? success "Answer"
    **B** — temp file + atomic rename + processed-record tracking.

??? note "Why"
    **Idempotent** = running twice has the same effect as running once. The recipe:
    build the output somewhere safe (temp), publish it in one atomic `mv` (a reader
    never sees a half-written file), and track what's been processed so reruns skip
    rather than duplicate.

    A is *nearly* right and fails on the half-written window (a crash mid-overwrite
    corrupts the output); C nukes state every run; D is concurrency arson. This is the
    foundation of the lookback-window pattern the FN shift asks about.

### Q12 · Storing currency with conversions · 🟢 Easy · ⭐
**Topic:** Data design · **Asked in:** T3-2025 AN + FN, ET-2

> When converting mixed-currency product feeds for analytics, why store the original currency along with the converted value?
>
> A. It is redundant and unnecessary.
> B. It enables recalculation if exchange rates change later.
> C. It doubles storage with no benefit.
> D. It makes queries faster.

??? success "Answer"
    **B** — keep the source amount + the rate used, so you can audit and recompute.

??? note "Why"
    A converted number is an *opinion at a point in time*. Store the original amount,
    the currency, and the rate you applied, and you can re-derive everything when rates
    change or a mistake is found — exactly what ET-2's rapid-fire list said: "store the
    original amount plus the specific exchange rate used to enable future audits."
    Losing the original (A, C) makes the conversion unfixable.

### Q14 · Fixing AI-generated production bugs · 🟡 Medium
**Topic:** Production practice · **Asked in:** T3-2025 AN

> Your pipeline classifies support tickets. A teammate used an AI assistant to write the code. It works in testing but occasionally produces unexpected categories in production. What is the best way to identify and fix this?
>
> A. Remove the AI-generated code and rewrite it from scratch.
> B. Capture production failures as test cases, fix the code, save the tests permanently.
> C. Accept occasional errors as normal and monitor the error rate.
> D. Disable the AI assistant for the entire team.

??? success "Answer"
    **B** — every production failure becomes a permanent regression test.

??? note "Why"
    The gold-standard loop: production misbehaviour → capture the offending input as a
    test → fix → the test guards it forever. Note what's *not* blamed: the code's
    authorship (AI or human — A, D) is irrelevant to the engineering; and "monitor and
    accept" (C) is how small bugs become outages. The exam consistently rewards
    **turning failures into fixtures**.

### Q15 · Reproducing a dataset months later · 🟡 Medium · ⭐
**Topic:** Reproducibility · **Asked in:** T3-2025 AN, ET-2

> Which provenance strategy most reliably supports reproducing a processed dataset months later when upstream providers may change?
>
> A. Only store the final processed CSV.
> B. Archive raw inputs, code, dependency versions, artifact hashes in a manifest.
> C. Rely on upstream to provide the same data again.
> D. Keep only commit timestamps.

??? success "Answer"
    **B** — raw data + code + pinned deps + hashes: the full recipe.

??? note "Why"
    Reproducibility means being able to *re-derive* the output, not just possess it
    (A). Upstream sources drift or vanish (C — the reason you archive raw inputs in the
    first place), and timestamps prove when, not what (D). The manifest with artifact
    hashes also catches silent corruption — a mismatched hash means your "same" input
    isn't.

    This is the theory under Docker's "pinned dependencies" answer and the FN shift's
    container-based reproducibility question — one concept, three costumes.

### Q16 · Scaling interactive cleaning · 🔴 Hard
**Topic:** Data cleaning architecture · **Asked in:** T3-2025 AN

> For scaling interactive data cleaning to large datasets while retaining reproducibility and human review, the best architecture is:
>
> A. Pure in-memory interactive tool for all rows.
> B. Sample-driven transforms as reusable ETL recipes with manual review flags.
> C. Manual spreadsheet edits for samples, then manual application.
> D. Single-run interactive session exported as final CSV.

??? success "Answer"
    **B** — clean a sample interactively, capture the operations as replayable code, review by exception.

??? note "Why"
    The tension: interactivity doesn't scale; batch processing doesn't invite human
    judgement. The professional resolution: **explore on a sample, record every
    transformation as code (the recipe), replay on the full dataset, flag edge cases
    for human review.** Reproducible *because* it's code; scalable *because* it's
    batch; human *because* flagged rows get eyes.

    A dies on memory, C and D never become reusable — the exam's longest, most
    detailed option is the architecturally sound one (the pattern the ET-2 session
    called out).

### Q17 · Schema validation for JSON providers · 🟡 Medium · ⭐
**Topic:** Validation · **Asked in:** T3-2025 AN, T1-2026 FN Q14 (Pydantic), ET-2

> When designing schema validation for heterogeneous JSON providers, the most robust rule set:
>
> A. Accept any valid JSON, even if it has extra fields.
> B. Enforce a schema with required fields, allowed types, and clear errors.
> C. Treat all values as text and avoid strict checks.
> D. Validate only a few fields to reduce processing time.

??? success "Answer"
    **B** — required fields + allowed types + clear error messages, enforced at the boundary.

??? note "Why"
    ET-2 named this the **fail-fast** strategy: audit types and value ranges the moment
    data arrives, reject with an error a human can act on. The alternatives are the
    failure modes you're choosing between: A and C let bad data flow until it corrupts
    something far from the cause; D validates a sample and hopes. Same concept as
    Pydantic at the API boundary — schema first, everything downstream trusts it.

### Q19 · Points within 5 km · ⛔

??? note "Transferable idea"

## Part 3 · Scenario 2 — weather API for event planning (Q23–27) · all current

> **The story (verbatim):** An event management company wants to automate weather data collection for planning outdoor events — fetching current weather and 5-day forecasts from a weather API for multiple cities.

### Q23 · The HTTP library · 🟢 Easy
> To make a request to the weather API, which Python library is most commonly used for HTTP requests?
>
> A. pandas  B. requests (or httpx)  C. flask  D. beautifulsoup

??? success "Answer"
    **B** — `requests` is the standard HTTP client (httpx its async-capable sibling).

??? note "Why"
    Tool selection again: pandas holds data, flask serves it, beautifulsoup parses
    *HTML* — only requests *makes HTTP calls*. The exam's wrong options are always
    real libraries from the wrong layer.

### Q24 · Where the API key lives · 🟢 Easy · ⭐⭐
> The API requires a key for authentication. Where should you store it to follow security best practices?
>
> A. Hard-coded in your script: `api_key = "abc123xyz"`.
> B. In an environment variable (e.g., `os.getenv('WEATHER_API_KEY')`).
> C. In a comment in the code.
> D. In the GitHub repository README.

??? success "Answer"
    **B** — environment variables (`.env` + `os.getenv`), never in code or repo.

??? note "Why"
    Third paper, same question, same answer — the `.env` workflow is the single most
    repeated security mark in the set. See [T1-2026 AN Q5](t1-2026-an.md#q5-what-goes-into-gitignore-medium-star)
    for the full reasoning; A, C, D here are just three flavors of publishing your key.

### Q25 · Reading the JSON response · 🟡 Medium · ⭐
> After calling the API, you want the weather description (e.g. "clear sky") from the JSON response. Which access is correct?
>
> A. `response['weather']['description']`
> B. `response_json['weather'][0]['description']`
> C. `response['main']['weather']`
> D. `response_json['description']['weather']`

??? success "Answer"
    **B** — `weather` is a **list**; you index `[0]` before reaching keys.

??? note "Why"
    The OpenWeather shape: `{"weather": [{"description": "clear sky", ...}], ...}`.
    Knowing JSON structure means knowing **lists vs objects** — `['weather']` returns
    an array, and chaining `['description']` straight onto an array is a `TypeError`.
    This pairs with `.text` vs `.json()` ([T1-2026 AN Q7](t1-2026-an.md#q7-requests-text-vs-json-easy-star)):
    parse first, then walk the structure it actually has.

    🟡 Also note the distractor style: every option uses the same words in different
    arrangements — reading the actual API shape is the only way through.

### Q26 · Respecting the rate limit · 🟢 Easy · ⭐
> You need weather for 10 cities; the API allows 60 calls per minute. How should you structure the code?
>
> A. Make all 10 requests simultaneously as fast as possible.
> B. Use a 1–2 sec `sleep()` between requests to avoid rate limits and handle errors.
> C. Ignore the rate limit since you're only making 10 calls.
> D. Make requests only during off-peak hours.

??? success "Answer"
    **B** — space the calls out and handle failures gracefully.

??? note "Why"
    10 < 60 *feels* safe (C) — but limits are often per rolling window and shared
    across keys/accounts, and bursts trip protection anyway. The professional pattern:
    **throttle + retry on 429 with backoff.** (Fun connection: our evaluator's aipipe
    calls hit exactly this — 60/minute, handled politely.)

    A is the anti-pattern (bursts get you throttled *harder*), D is folk superstition.

### Q27 · The 401 diagnosis · 🟢 Easy · ⭐⭐
> The API request fails with a 401 error status code. What does this indicate?
>
> A. The API server is down.  B. Unauthorized — likely an invalid or missing API key.  C. The city name is misspelled.  D. Too many requests (rate limit exceeded).

??? success "Answer"
    **B** — 401 = authentication failed: check the key.

??? note "Why"
    The 401 twin of [Q4](#q4-http-401-easy-starstar), now inside a scenario. Note the
    error-code decision tree forming: key problems (401) vs client request problems
    (404, misspelled city) vs throttling (429) vs server down (5xx). Diagnosis by
    status code is a free mark every time it appears.

## Part 4 · Scenario 3 — LLM sentiment analysis (Q28–32) · all current, W3 territory

> **The story (verbatim):** A product team wants to analyze customer feedback from 500 app reviews (text + 1–5 star ratings), using an LLM to classify sentiment (positive/negative/neutral) and extract themes, instead of manual review.

### Q28 · The HTTP verb for the LLM call · 🟢 Easy · ⭐
> To send a review to an LLM API for sentiment analysis, which HTTP request would you typically make?
>
> A. GET request to retrieve sentiment.  B. POST request with the review text in the request body.  C. DELETE request to remove the review.  D. PUT request to update the review.

??? success "Answer"
    **B** — POST: you submit a payload for processing.

??? note "Why"
    The scenario version of the GET-vs-POST short answer ([T1-2026 FN
    Q25](t1-2026-fn.md#q25-get-or-post-medium)): LLM inference *processes* submitted
    data — POST by REST semantics, payload in the body, not the URL. Here it's one
    mark; there it was 2 marks of writing — same knowledge, escalating format.

### Q29 · Designing the prompt · 🟢 Easy · ⭐
> When designing a prompt for the LLM to classify sentiment, which structure is most effective?
>
> A. Just send the review text with no instructions.
> B. Provide clear instructions and specify the desired output format: "Classify the sentiment of this review as positive, negative, or neutral. Review: {review_text}"
> C. Send only the word "sentiment".
> D. Ask the LLM to write code instead.

??? success "Answer"
    **B** — instruction + output contract + the data, clearly separated.

??? note "Why"
    Prompt anatomy (course W3 in one mark): **say what to do, define the output format,
    then supply the input**. A gives the model a riddle; C is a password attempt; D
    changes the task. The `{review_text}` placeholder also matters — separating
    instruction from data is the same discipline as system-vs-user prompts.

### Q30 · Cost and scale awareness · 🟡 Medium
> You're analyzing 500 reviews. Each API call costs $0.002 and takes 2 seconds. What practical considerations should guide your approach?
>
> A. Send all 500 reviews in a single API call.
> B. Process reviews in batches, track costs, handle errors, and cache results.
> C. Only analyze 5 reviews to save money.
> D. Call the API repeatedly for the same review.

??? success "Answer"
    **B** — batch, budget, handle failures, and never pay twice for the same input.

??? note "Why"
    Production LLM thinking in one option: **batch** (rate limits, throughput), **track
    costs** (it's real money — our evaluator measures spend per run for exactly this
    reason), **handle errors** (retries, fallbacks), **cache** (identical input →
    stored output — the FastAPI-cache scenario from the Jan papers). A exceeds context
    limits, C abandons the task, D is literally burning money.

### Q31 · Inconsistent output formats · 🟡 Medium · ⭐
> The LLM returns "negative", "Negative", "neg" inconsistently. How do you handle this?
>
> A. Manually review and edit each response before analysis.
> B. Use prompt engineering to enforce the exact output format ("Respond with exactly one word: positive, negative, or neutral in lowercase").
> C. Ignore the inconsistencies and use responses as they are.
> D. Switch to a different LLM for each review.

??? success "Answer"
    **B** — constrain the output contract in the prompt.

??? note "Why"
    LLMs are stochastic; **your prompt must pin the format** if downstream code parses
    it. This is the lighter sibling of Structured Outputs ([T1-2026 AN
    Q20](t1-2026-an.md#q20-what-structured-outputs-guarantees-medium-star)): prompt
    enforcement (mostly works) vs schema-constrained generation (guaranteed). A
    doesn't scale, C poisons your counts ("neg" ≠ "negative" to `==`), D is chaos.

    🟢 Chain worth memorizing: *pin the format in the prompt → validate the response →
    escalate to Structured Outputs when it must never break.*

### Q32 · Computing the percentage · 🟢 Easy
> After classifying all reviews, you want the percentage that are negative. Which approach is correct?
>
> A. Manually count negative reviews.  B. Use a DataFrame, count rows with sentiment 'negative', divide by total, multiply by 100.  C. Ask the LLM to calculate the number of negative reviews.  D. Count only positive reviews.

??? success "Answer"
    **B** — the computation belongs in *your* code, on structured data.

??? note "Why"
    Division of labour: the LLM judges each review; **pandas does the math.** Asking the
    LLM to count (C) re-introduces hallucination into a step that should be exact —
    the same principle as our judge: the model returns verdicts, JavaScript sums them.
    `(df['sentiment'] == 'negative').mean() * 100` and you're done.

## Part 5 · Scenario 4 — RAG support chatbot (Q33–37) · all current — W4 is a whole RAG week

> **The story (verbatim):** An e-commerce company builds a customer support chatbot answering questions about products, policies and orders. Instead of training a custom model, they use RAG (Retrieval Augmented Generation): retrieve relevant information from their knowledge base (500 product manuals, FAQs, policy documents) and generate responses. Components: a vector database storing document embeddings for similarity search, the LLM generating from retrieved context, and a chunking strategy that breaks documents into smaller pieces.

### Q33 · Why chunk documents · 🟡 Medium · ⭐
> In a RAG system, what is the purpose of breaking documents into smaller chunks before storing them?
>
> A. To save storage space in the database.
> B. To match queries with relevant sections, not whole documents, for better accuracy.
> C. To make documents easier to read for humans.
> D. To reduce the cost of LLM API calls.

??? success "Answer"
    **B** — retrieval works on passages; the right 2 paragraphs beat a whole manual.

??? note "Why"
    Embeddings compress meaning into one vector — a whole manual averages into
    mush, and even if retrieved, it blows the context window. A chunk (a policy
    paragraph, an FAQ entry) embeds sharply and retrieves precisely: the query
    "return policy?" matches the *returns* chunk, not the 40-page manual that
    contains it. Accuracy, not storage (A) or readability (C).

### Q34 · What happens first · 🟡 Medium · ⭐
> When a user asks "What is your return policy?", which step happens FIRST in a RAG system?
>
> A. Generate a response directly using the LLM.
> B. Convert the query to an embedding and search for similar chunks.
> C. Store the user's question in the database for future use.
> D. Send an email to customer support.

??? success "Answer"
    **B** — embed the query, retrieve, *then* generate. R = the first letter.

??? note "Why"
    The pipeline order is the question: **Retrieve → Augment → Generate.** A is
    answering without looking anything up (hallucination risk — the exact failure RAG
    exists to prevent); C and D are workflow fantasies. If you remember one sentence
    about RAG: *the query is embedded and matched against chunk embeddings before the
    LLM sees anything.*

### Q35 · Stale answers from old manuals · 🔴 Hard · ⭐
> The chatbot sometimes returns information from outdated product manuals even though newer versions exist. What is the most likely cause?
>
> A. The LLM relies on outdated training data instead of current documents.
> B. Old document chunks remain in the vector database and weren't updated.
> C. The document chunking strategy was applied incorrectly or inconsistently.
> D. The embedding model is too small to capture document differences accurately.

??? success "Answer"
    **B** — the index holds both versions; retrieval doesn't know which is current.

??? note "Why"
    RAG's Achilles heel: **the vector database is a snapshot.** Ingest v1 of the
    manual, ship v2, forget to remove v1's chunks — now both embed, both retrieve, and
    the LLM can't tell which is authoritative. The fix is operational: re-ingest
    atomically, version or timestamp chunks, expire the old.

    A is the seductive option — "outdated info" *sounds* like training data — but RAG's
    whole point is that answers come from retrieved context, not the model's memory.
    The bug is in the index, not the brain.

### Q36 · Choosing the chunk size · 🟡 Medium · ⭐
> When choosing chunk size for a customer support use case, which approach provides the best balance?
>
> A. Very small chunks (1–2 sentences) for highly precise matches.
> B. Medium chunks (1–2 paragraphs, ~200–500 words) for context and focus.
> C. Very large chunks (entire documents) to provide maximum context.
> D. Randomly sized chunks to introduce variety.

??? success "Answer"
    **B** — medium chunks balance retrieval precision against context completeness.

??? note "Why"
    The chunk-size trade-off is *the* RAG tuning knob: too small and a retrieved
    fragment lacks the context to answer (Q35's manual needs its surrounding
    paragraph); too large and embeddings blur plus context windows overflow (Q33's
    whole-manual problem). ~200–500 words is the working middle the course teaches.
    Course W4 dedicates a file to chunking strategies — this is examinable at full
    depth, not just this one mark.

### Q37 · How the LLM uses retrieved chunks · 🟢 Easy · ⭐
> A customer asks "Can I return my laptop if I opened the box?" The chatbot retrieves two relevant chunks: one about return policy, one about laptop specifications. How does the LLM use these?
>
> A. It ignores the retrieved chunks and answers from training data.
> B. It uses the chunks as context to generate an informed answer.
> C. It copies text from the chunks verbatim without changes.
> D. It stores the retrieved chunks for future queries.

??? success "Answer"
    **B** — chunks are grounding context; the model synthesizes an answer from them.

??? note "Why"
    "Augmented" in RAG: the prompt carries the retrieved chunks *plus* the question,
    and the LLM composes grounded on them. Not ignored (A — that's the hallucination
    path), not regurgitated (C — synthesis handles "opened box" which no chunk states
    verbatim). This is the **G** step of Retrieve→Augment→Generate, and the concept
    behind W4's "grounded answers" and GA4's `grounded-answer-api` question.
