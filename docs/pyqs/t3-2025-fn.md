### Q2 · Parquet for large arrays · 🟢 Easy · ⭐⭐
**Topic:** Data formats · **Asked in:** T3-2025 FN + AN family, T1-2026 AN Q4, ET-2

> Which data serialization format is most efficient for storing large numeric arrays with minimal overhead?
>
> A. XML  B. Parquet  C. JSON  D. Plain text CSV

??? success "Answer"
    **B** — Parquet: columnar, binary, typed, compressed.

??? note "Why"
    The professor's own "odd one out": XML, JSON and CSV are all **text-based** (and
    row-oriented for data); Parquet is the columnar binary outlier. For large numeric
    arrays it wins on every axis — no text-parsing overhead, type-aware compression,
    and queries that touch only the columns they need. Full reasoning: [T1-2026 AN
    Q4](t1-2026-an.md#q4-why-parquet-beats-csv-medium-star).

### Q3 · git diff · 🟢 Easy · ⭐
**Topic:** Git · **Asked in:** T3-2025 FN, ET-2, course W1

> In Git, which command shows the differences between your working directory and the last commit?
>
> A. `git status`  B. `git diff`  C. `git log`  D. `git show`

??? success "Answer"
    **B** — `git diff` shows the line-by-line changes.

??? note "Why"
    The inspection family from ET-2 (the professor called status+diff your "safety
    goggles before welding" — i.e., before committing):

    - `git status` — *which files* changed/staged/untracked
    - `git diff` — *what lines* changed, working directory vs last commit
    - `git log` — the commit *history* (who, when, message)
    - `git show` — one specific commit's changes in detail

    🟡 **Trap:** `git diff` after `git add` shows *nothing* — by default it compares the
    working directory to the **staging area**. `git diff --staged` shows staged-vs-commit.

### Q8 · Late-arriving orders · 🟡 Medium · ⭐⭐
**Topic:** ETL design · **Asked in:** T3-2025 FN, ET-2 (named twice)

> You are building a daily ETL pipeline that processes customer orders. Orders can arrive late or be updated. Which design pattern ensures you don't miss late-arriving data while avoiding duplicate processing?
>
> A. Process only data from the current day and ignore anything older.
> B. Use lookback windows with deduplication based on unique order IDs and update timestamps.
> C. Reprocess all historical data every day to ensure completeness.
> D. Process data as it arrives without tracking what has been processed.

??? success "Answer"
    **B** — re-read the last N days, upsert on ID + timestamp, skip what you've seen.

??? note "Why"
    The professor's flagship ETL pattern, named in both revision sessions: a **lookback
    window** (process the last ~3 days, not just today) catches late arrivals, while
    **deduplication on (order_id, updated_at)** means re-seeing a row is harmless — the
    newest version wins.

    C is the trap the professor called "a failure of design": full reprocessing burns
    compute, takes hours, and locks the database — for data you already have. A loses
    the late rows (the stated symptom); D has no memory at all. This is also GA2's
    `api-idempotency-pagination` question and the grown-up version of [T3-2025 AN
    Q11's idempotency](t3-2025-an.md#q11-idempotent-etl-scripts-medium-star).

### Q9 · Caching an hourly-updated dashboard · 🟡 Medium · ⭐⭐
**Topic:** Caching · **Asked in:** T3-2025 FN, T1-2026 both shifts, ET-1 + ET-2

> Your analytics dashboard queries a large dataset that updates hourly but is queried every few seconds by users. Which caching strategy improves performance while maintaining reasonable freshness?
>
> A. Never cache — always query the live dataset directly.
> B. Cache results with a TTL matching the update frequency, and invalidate on updates.
> C. Cache results permanently without refreshing.
> D. Disable the dashboard whenever the dataset is updated.

??? success "Answer"
    **B** — TTL tuned to the data's update rhythm.

??? note "Why"
    The workload is asymmetric: 1 update/hour vs ~3600 reads/hour — perfect caching
    conditions. A **5-minute TTL** means the database is hit once per interval instead
    of every few seconds (the professor's exact arithmetic), and freshness loss is
    bounded by the TTL itself.

    This is the TTL concept wearing its systems-design costume — the same family as
    `max-age=3600` ([T1-2026 AN Q19](t1-2026-an.md#q19-what-max-age3600-does-easy-starstar))
    and the cache-buster ([T1-2026 AN Q22](t1-2026-an.md#q22-forcing-fresh-data-past-the-cache-easy-starstar)):
    TTL = freshness budget, set it to what the data tolerates.

### Q10 · Joining across timezones · 🔴 Hard · ⭐
**Topic:** Data joining · **Asked in:** T3-2025 FN, ET-2

> When joining datasets from different time zones, you discover that some timestamps lack timezone information. What is the safest approach?
>
> A. Assume all missing timestamps are in UTC for simplicity.
> B. Infer the timezone from metadata or location, document assumptions, and flag inferred values.
> C. Reject any records without explicit timezone information.
> D. *(distractor: a pandas parsing error claim)*

??? success "Answer"
    **B** — infer where you can, write down what you assumed, mark the rows.

??? note "Why"
    Silent assumptions are how **silent data corruption** happens: a "UTC" guess that's
    actually local time shifts every join by hours — orders appear before they were
    placed. The professional recipe: infer from evidence (metadata, geography),
    **document** the assumption, and **flag** inferred rows so auditors and downstream
    users know what's certain vs guessed.

    A is the tempting shortcut (and the classic mistake the question exists to catch);
    C throws away real data over metadata. The professor's phrasing: assume-and-forget
    is the bug; assume-and-document is engineering.

### Q13 · Fixing biased recommendations · 🟡 Medium
**Topic:** ML practice · **Asked in:** T3-2025 FN, ET-2 (rapid-fire)

> Your recommendation system performs significantly worse for certain user segments. What is the best systematic approach to diagnose and fix this?
>
> A. Retrain the model with more data and hope it improves.
> B. Analyze performance by segment, identify biases in training data, add segment-specific tests, and validate fixes.
> C. Disable recommendations for poorly performing segments.
> D. Manually override recommendations for affected users.

??? success "Answer"
    **B** — measure per segment, find the data cause, guard with tests, prove the fix.

??? note "Why"
    The diagnosis pattern: an *aggregate* score hides *segment* failures, so the first
    move is **slicing the metrics**. Then the cause is usually training data (a segment
    underrepresented), and the fix earns trust only with segment-level tests — the same
    "turn failures into tests" discipline as [T3-2025 AN Q14](t3-2025-an.md#q14-fixing-ai-generated-production-bugs-medium).

    A is "have you tried throwing more data at it" (hope isn't a method); C and D
    hide the problem from the affected users — the opposite of fixing it.

### Q14 · Vulnerable dependency with breaking changes · 🟡 Medium · ⭐
**Topic:** Dependency management · **Asked in:** T3-2025 FN, ET-2 (rapid-fire), T1-2026 AN Q14

> Your pipeline uses a third-party library with known security vulnerabilities in older versions. The latest version includes breaking API changes. What should you do?
>
> A. Stay on the older vulnerable version to avoid breaking existing code.
> B. Assess vulnerability severity, test the new version in staging, and plan migration or patches.
> C. Update to the latest version immediately without any testing.
> D. Replace the library entirely with custom code regardless of complexity.

??? success "Answer"
    **B** — weigh the risk on both sides, verify in isolation, then move deliberately.

??? note "Why"
    The dependency question at its hardest: **two risks in tension** — the
    vulnerability you're exposed to vs the breakage the upgrade might cause. The
    professional move is measured on both scales: how severe is the CVE (is it even
    reachable in your usage?), and does the new version pass *your* tests in staging?

    A ignores a known security hole; C is the "immediately upgrade" pole that every
    paper marks wrong ([T3-2025 AN Q13](t3-2025-an.md#q13-upgrading-a-supported-dependency-easy-star)'s
    option A); D rewrites a library because updating it seemed scary.

### Q16 · Data lineage metadata · 🔴 Hard
**Topic:** Data engineering · **Asked in:** T3-2025 FN

> When implementing data lineage tracking for a complex pipeline with multiple sources, transformations, and outputs, which metadata is most critical to capture?
>
> A. Capture only the final output location of the pipeline.
> B. Capture source IDs, transformation versions, timestamps, data quality metrics, and dependencies.
> C. Capture only the names of users who executed the pipeline.
> D. Capture only storage costs and query performance metrics.

??? success "Answer"
    **B** — the full provenance chain: where data came from, what version of what touched it, when, how well.

??? note "Why"
    **Lineage** answers "where did this number come from?" — and for a number in a

### Q17 · PII data minimization · 🟡 Medium · ⭐
**Topic:** Privacy · **Asked in:** T3-2025 FN, ET-2 (rapid-fire)

> Your pipeline processes personally identifiable information (PII). A privacy audit requires data minimization. Which strategy best balances utility and privacy?
>
> A. Encrypt all data and continue processing it without changes.
> B. Keep only necessary fields, anonymize or aggregate data, enforce access controls, and document retention.
> C. Delete all PII immediately without considering business requirements.
> D. Move PII to a separate database while keeping the same access patterns.

??? success "Answer"
    **B** — collect less, mask what remains, restrict who, and say how long.

??? note "Why"
    The four pillars of **data minimization**: field-level necessity (does the analysis
    need the phone number, or the country?), anonymization/aggregation (the analysis
    often survives on less), access control (fewer hands), and retention policy
    (documented, enforced). It's a *balance* — the business still functions.

    A is the classic pseudo-compliance: encryption protects at rest, but the pipeline
    then *decrypts and processes* everything anyway — minimization means not holding
    what you don't need. C is privacy at the cost of the product; D relocates the
    problem without changing exposure.

## Part 2 · Scenario 1 — restaurant reviews with pandas (Q18–22) · all current — the professor's ET-2 case study

> **The story (verbatim):** A food delivery platform analyzes restaurant reviews (CSV with ratings, text comments, timestamps) to find trending cuisines and satisfaction patterns.

### Q18 · Missing review text · 🟢 Easy · ⭐
> The dataset has missing values in `review_text` (ratings without comments). Before analyzing review text for common words, what should you do?
>
> A. Ignore missing values and let pandas handle them automatically.
> B. Remove rows with missing review text using `df.dropna(subset=['review_text'])`.
> C. Replace missing entries with the word "missing".
> D. Delete the entire review_text column.

??? success "Answer"
    **B** — drop the rows lacking the thing you're analyzing.

??? note "Why"
    The professor's **NLP trap** from ET-2: for *text* analysis, rows with no text are
    pure noise — they'd pollute word counts as `NaN` (A) or, catastrophically, make
    "missing" the most common word in your corpus (C). `dropna(subset=[...])` targets
    exactly the column you need. D sacrifices the whole analysis for one column's
    hygiene.

    🟡 Note the *scope*: you're dropping rows only for the text analysis — their
    **ratings** still count elsewhere. Cleaning is per-question, not global.

### Q19 · Words in negative reviews · 🟢 Easy
> To identify the most common words in negative reviews (rating < 3.0), which approach correctly combines filtering and text analysis?
>
> A. Count all words in all reviews regardless of rating.
> B. Filter for low ratings, then extract and count words from the review_text column.
> C. Sort reviews by rating and manually read the bottom ones.
> D. Use only the rating numbers without looking at text.

??? success "Answer"
    **B** — filter first, then aggregate: two composable steps.

??? note "Why"
    Pandas thinking in miniature: `df[df['rating'] < 3]['review_text']` → split/count
    words. The filter and the analysis are independent operations chained — which is
    why B is phrased as a pipeline. A answers a different question (all reviews), C
    doesn't scale, D ignores the text entirely.

### Q20 · Sharing results with non-technical stakeholders · 🟢 Easy · ⭐
> After the analysis, which file format is most appropriate for sharing summary results (e.g., average rating by cuisine) with non-technical stakeholders?
>
> A. Python pickle file (`.pkl`)  B. CSV file that can be opened in Excel  C. JSON with nested structures  D. Binary database file

??? success "Answer"
    **B** — CSV: universal, opens in Excel, no code required.

??? note "Why"
    ET-2's stakeholder rule: **know your audience's tools.** A non-technical manager
    lives in Excel/Sheets — CSV is the lowest common denominator that just works.
    Pickle requires Python (and is a security risk to open!), JSON needs a programmer,
    a database file needs a database. The professor's phrasing: "why a CSV is the best
    format for a non-technical manager — portability and ease of use."

### Q21 · The library for tabular CSV · 🟢 Easy
> Which Python library is most commonly used for loading and analyzing tabular CSV data like this dataset?
>
> A. requests  B. pandas  C. BeautifulSoup  D. Flask

??? success "Answer"

??? note "Why"
    Tool selection, one mark: requests fetches, BeautifulSoup parses HTML, Flask

### Q22 · Average rating per cuisine · 🟢 Easy · ⭐⭐
> To find the average rating for each cuisine type (Indian, Italian, Japanese), which pandas operation is most appropriate?
>
> A. `df.sort_values('cuisine')`  B. `df.groupby('cuisine')['rating'].mean()`  C. `df.filter('cuisine')`  D. `df.merge('cuisine', 'rating')`

??? success "Answer"
    **B** — groupby + aggregate: split cuisine groups, apply mean, combine.

??? success "The professor taught this exact line in ET-2"
    ```python
    df.groupby('cuisine')['rating'].mean()
    ```

??? note "Why"
    **groupby = split–apply–combine**: split rows by cuisine, apply `mean()` to each
    group's ratings, combine into one table. The wrong options are real pandas verbs
    pointed at the wrong job — sort arranges but doesn't aggregate, `filter` selects
    *rows* by condition (and takes callables, not column names), merge joins
    *dataframes* (not column names — the syntax is nonsense). This one line appeared
    verbatim in the session, the GA, and this paper: **free marks**.

## Part 3 · Scenario 2 — the team Git workflow (Q23–27) · all current, course W1

> **The story (verbatim):** A data science team uses Git on a shared project. Members work on separate feature branches and merge into main through pull requests. Setup: `main` (production-ready), `dev` (development), feature branches (e.g., `feature-data-cleaning`).

### Q23 · The save-and-upload sequence · 🟢 Easy · ⭐
> After making changes to your code, what is the correct sequence to save your work and upload it to GitHub?
>
> A. `git push` → `git add` → `git commit`
> B. `git commit` → `git add` → `git push`
> C. `git add` → `git commit` → `git push`
> D. `git merge` → `git push`

??? success "Answer"
    **C** — stage, commit, push. Always in that order.

??? note "Why"
    The pipeline is one-directional: working directory --`add`--> staging --`commit`-->
    local history --`push`--> remote. Pushing *before* committing (A) sends nothing;
    committing *before* staging (B) commits an empty snapshot; merge isn't part of
    saving at all (D). If you can narrate the diagram, no option can confuse you.

### Q24 · The merge conflict · 🟡 Medium · ⭐
> Two team members both modify the same line in `analysis.py` on different branches. When the second person tries to merge, what will happen?
>
> A. Git automatically keeps the newer change.
> B. Git creates a merge conflict that must be resolved manually by choosing which change to keep.
> C. Git deletes both changes.
> D. Git randomly picks one change.

??? success "Answer"
    **B** — conflict markers appear; a human decides.

??? note "Why"
    Git tracks *what* changed, not *who was right*: two edits to the same lines of
    history is a genuine ambiguity no algorithm should resolve silently. Git pauses the
    merge, marks the file (`<<<<<<<` / `=======` / `>>>>>>>`), and the second merger
    edits the file to the intended truth, then commits the resolution.

    A, C, D all describe silent decisions — and silent decisions on someone's code are
    exactly what version control exists to prevent.

### Q25 · Getting the latest main · 🟢 Easy · ⭐
> Before pushing your changes, you want your branch to have the latest updates from main. Which command downloads and integrates those updates?
>
> A. `git commit main`  B. `git pull origin main` (while on your feature branch)  C. `git delete main`  D. `git init main`

??? success "Answer"
    **B** — pull = fetch + merge, bringing main's commits into your branch.

??? note "Why"
    `git pull origin main` while on your feature branch fetches the remote main and
    merges it into what you're on — update-before-push, the habit that prevents most
    conflicts. (Its cousins: `git fetch` downloads without merging; `git pull --rebase`
    replays your commits on top for a linear history — beyond the exam, useful in life.)

### Q26 · Why pull requests exist · 🟢 Easy · ⭐
> What is the main purpose of creating a pull request (PR) instead of directly merging your branch into main?
>
> A. Pull requests are faster than merging.
> B. Pull requests allow team members to review your code, suggest changes, and approve before merging.
> C. Pull requests automatically fix bugs.
> D. Pull requests are only for documentation.

??? success "Answer"
    **B** — the review gate: other humans read, comment, and approve before code lands.

??? note "Why"
    A PR is a **conversation about a merge**: reviewers see the diff, comment, request
    changes, and the branch merges only when approved. It's how a team shares
    responsibility for what enters main — the story's whole workflow (feature branch →
    PR → review → merge) exists to make "production-ready" mean something.

### Q27 · Creating a feature branch · 🟢 Easy · ⭐
> When starting work on a new feature, what is the correct Git command sequence to create and switch to a new branch called `feature-analysis`?
>
> A. `git commit feature-analysis`
> B. `git branch feature-analysis` then `git checkout feature-analysis`
> C. `git push feature-analysis`
> D. `git merge feature-analysis`

??? success "Answer"
    **B** — create the branch, then switch to it. (Shorthand: `git checkout -b feature-analysis`.)

??? note "Why"
    Two steps, two verbs: `branch` creates a pointer, `checkout` moves your working
    directory onto it — after which commits land on the branch, not main. The one-liner
    the ET-2 session taught: `git checkout -b feature-analysis` does both. A, C, D use
    commit/push/merge — verbs for later stages of the branch's life, not its birth.

## Part 4 · Scenario 3 — deploying the Streamlit dashboard with Docker (Q28–32) · all current, course W2

> **The story (verbatim):** A team builds a Python dashboard using Streamlit visualizing sales data, and packages it with Docker so anyone can access it via a browser.

### Q28 · Running with the port published · 🟢 Easy · ⭐⭐
> After building the Docker image, which command correctly runs the container and makes the dashboard accessible on port 8501?
>
> A. `docker build -t dashboard .`  B. `docker run -p 8501:8501 dashboard`  C. `docker push dashboard`  D. None of these

??? success "Answer"
    **B** — `docker run -p 8501:8501` publishes host:container.

??? note "Why"
    The `-p host:container` flag is the bridge that makes the container's port visible
    on your machine (full story in [T1-2026 AN Q28](t1-2026-an.md#q28-expose-vs--p-easy-starstar)).
    A builds (no run), C uploads to a registry (nothing runs locally). Streamlit's
    default port is 8501 — worth knowing since both papers use it.

### Q29 · Reading the crash logs · 🟢 Easy · ⭐
> The dashboard application crashes when deployed. Which Docker command shows the application's error messages and logs?
>
> A–D. *(options were command images)* — **Answer marked: `docker logs <container>`.**

??? note "Why"
    A container that exits still has its stdout/stderr captured: `docker logs <container>`
    replays them — the first stop for any container crash. Its cousins: `docker ps`
    (what's running), `docker exec -it <container> bash` (step inside a *live*
    container), `docker compose logs` (whole stack). When something dies in a box, the
    box keeps the diary.

### Q30 · Why Docker for deployment · 🟢 Easy · ⭐⭐
> What is the main advantage of using Docker to deploy the dashboard?
>
> A. Docker makes the code run faster.
> B. Docker packages the application with all dependencies in a container, ensuring it runs consistently across different machines.
> C. Docker automatically writes code for you.
> D. Docker provides free hosting.

??? success "Answer"
    **B** — the whole environment ships together; every machine becomes the same machine.

??? note "Why"
    Docker's elevator pitch, asked in some form in **all four papers** (see [T1-2026 FN
    Q5](t1-2026-fn.md#q5-docker-on-windows-easy-star)): OS + runtime + libraries +
    code, sealed into one artifact. "Works on my machine" stops being an excuse.
    Docker does not speed code up (A), write it (C), or host it for free (D) — the
    registry and runtime still cost someone something.

### Q31 · The Dockerfile install line · 🟢 Easy · ⭐⭐
> In the Dockerfile, which command specifies which Python packages should be installed in the container?
>
> A. `RUN pip install -r requirements.txt`  B. `COPY dashboard.py`  C. `EXPOSE 8501`  D. `FROM python:3.11`

??? success "Answer"
    **A** — RUN executes at build time; pip installs the listed packages into the image.

??? note "Why"
    The Dockerfile verbs: `FROM` names the base image, `COPY` brings files in, `RUN`
    **executes** commands during the build, `EXPOSE` documents a port. Only RUN
    installs anything — this is the third paper carrying the `RUN pip install` answer
    ([T1-2026 FN Q11](t1-2026-fn.md#q11-the-missing-pip-install-medium-star)).

### Q32 · What EXPOSE does · 🟢 Easy · ⭐⭐
> The Dockerfile includes the line `EXPOSE 8501`. What does this do?
>
> A. Automatically makes the application accessible to anyone on the internet.
> B. Documents the listen port; you must still publish it using `-p 8501:8501`.
> C. Closes port 8501 for security.
> D. Changes the application code to use port 8501.

??? success "Answer"
    **B** — EXPOSE is documentation; `-p` is the actual bridge.

??? note "Why"
    Third appearance ([T1-2026 AN Q28](t1-2026-an.md#q28-expose-vs--p-easy-starstar)),
    now as its own question. The professor's one-liner from ET-2: **EXPOSE is a label;
    `-p` is the bridge.** If a container runs but `localhost:8501` refuses to connect,
    you forgot `-p` — the single most Docker question in the corpus.
